# 物品与个人模特三维能力调研

核对日期：2026 年 10 月 20 日。源码基线：2.61.1，提交 `c4ac3c62`，Room 30，备份格式 10。

后续方向：用户已选择现阶段不做真实三维，转为评估[借鉴宠物序列帧的二维预览](pet-style-wardrobe-preview-research-2026-10-20.md)。下文保留三维技术调研，不作为当前实施计划。

Lolita 可以逐步支持可旋转的物品和个人模特。优先验证本地 GLB 查看、统一人体和独立物品的装配，再评估照片建模服务。真正可换装的三维试衣还需要人体、服装、尺寸、变形与遮挡协同；把现有试衣照片转成一个三维人物，只能先得到整套造型的展示资产。

本次是技术与产品可行性调研，以下接入结构及阶段为建议，没有实现新增功能。新增付费调用 0 次，未向新服务上传人物或商品照片。

## 当前应用基础

| 现有能力 | 实际数据与执行方式 | 对三维支持的影响 |
| --- | --- | --- |
| 物品图片与规格 | `Item.imageUrls`、尺码图、`specificationsJson` | 可以提供建模参考和原始证据，没有网格、材质、骨骼或挂点 |
| 我的模特 | `PersonalModel` 保存原照、参数请求及确认后的 `imageUrl` | 目前是二维人物底图；`model` 是生成服务型号，不是三维文件 |
| 身体参数 | `BodyMeasurements` 包含身高、体重及可选胸腰臀、肩宽、内侧腿长 | 可作为未来拟合输入；现实现把参数写进生图提示词，没有测量或约束输出网格 |
| 人台与试衣 | 生成器返回图片字节，`ImageTask.resultImagePath` 保存结果 | 后台任务经验可复用，但结果类型和执行协议不能直接容纳 GLB |
| 文件与备份 | `ImageFileHelper` 校验并解码图片；ZIP 重映射 `images/` 引用 | GLB 需要独立文件校验、引用、删除与备份处理，不能塞入图片路径冒充图片 |
| Android 渲染 | Compose 与 Coil 等图片组件，没有三维引擎依赖 | 需要增加渲染与生命周期管理，并核对现有 Haze、手势和导航 |

对应源码：[Item](../app/src/main/java/com/lolita/app/data/local/entity/Item.kt)、[PersonalModel](../app/src/main/java/com/lolita/app/data/local/entity/PersonalModel.kt)、[身体参数与生成请求](../app/src/main/java/com/lolita/app/domain/model/PersonalModel.kt)、[个人模特生成器](../app/src/main/java/com/lolita/app/data/personalmodel/PersonalModelGenerator.kt)、[ImageTask](../app/src/main/java/com/lolita/app/data/local/entity/ImageTask.kt)、[任务执行器](../app/src/main/java/com/lolita/app/data/generation/ImageTaskRunner.kt)、[图片文件管理](../app/src/main/java/com/lolita/app/data/file/ImageFileHelper.kt)、[备份](../app/src/main/java/com/lolita/app/data/file/BackupManager.kt)、[依赖](../app/build.gradle.kts)。

## 能力层次与采用顺序

| 目标 | 可采用的方式 | 主要条件 | 建议 |
| --- | --- | --- | --- |
| 物品三维查看 | 导入 GLB，旋转、缩放、重置视角 | 文件完整、材质可渲染，性能适合手机 | 先做 |
| 照片生成物品 | 单图或真实多视图生成网格和纹理 | 逐件检查造型、背面、薄片与细节 | 独立评估服务 |
| 可调个人模特 | 同一拓扑的人体、骨骼和体型形变 | 参数到形状的拟合、尺度和围度校准 | 与查看原型同步研究 |
| 模特穿戴物品 | 独立物品挂点，或按人体变形的服装 | 统一姿态、坐标、尺度、层次及碰撞处理 | 先固定站姿和少量品类 |
| 整套造型三维展示 | 将已穿衣人物重建为完整模型 | 接受衣服与身体可能连成整体 | 可作为单独展示用途 |
| 真实合身与布料动态 | 版片、缝线、物性、人体及求解器 | 有可信尺寸和材料，完成专项验证 | 后续专业路线 |

这几层需要分别验收。能打开 GLB 不证明商品还原；能给人物绑定骨骼不证明衣服可独立脱换；能播放动画也不证明重新计算了布料受力。

## Android 渲染方案

建议以 glTF 2.0 的二进制格式 GLB 作为首期交付格式，并优先接收纹理内嵌的文件，减少模型与贴图分离后的丢失和恢复问题。

| 方案 | 已有支持 | 与本项目的关系 |
| --- | --- | --- |
| SceneView 与 Filament | Compose 三维场景、GLB 加载、相机控制；Filament 支持 PBR 材质、骨骼和形变动画 | 首选研究方向，适合与现有 Compose 页面连接。[SceneView](https://github.com/sceneview/sceneview)、[Filament](https://github.com/google/filament) |
| Filament 与 AndroidView | 官方 Android 库和 SurfaceView、TextureView 渲染入口 | SceneView 兼容成本过高时的备选，需要自己管理相机、手势及资源释放。[Android 接入](https://github.com/google/filament#android) |
| model-viewer | 浏览器模型展示、相机交互和 AR 入口 | 适合快速查看外部样本；正式采用 WebView 仍需核对本地资源、手势与渲染开销。[官方项目](https://modelviewer.dev/) |

当前项目是 Kotlin 2.1.0、Compose BOM 2024.12.01、compileSdk 35。SceneView 当前 main 的依赖已使用较新的 Kotlin 与 Compose，不能直接认定最新版本可以加入现有工程。实施时先在独立样例中验证固定版本，比较兼容 SceneView 与直接 Filament 的代价，不为一个查看器预先升级整套应用。[当前依赖声明](https://github.com/sceneview/sceneview/blob/main/gradle/libs.versions.toml)

Filament 的布料材质着色描述光线如何作用于布面，不负责由版片求解垂坠、松量或受力。七套皮肤可以改变查看器外围、背景与操作组件；商品本身的颜色和材质应保持一致。

## 物品建模服务

| 候选 | 官方公开能力 | 采用条件 |
| --- | --- | --- |
| 腾讯混元生 3D | 专业版 3.0、3.1，支持图生、真实多视图、白模、纹理及拓扑；3.1 支持八视图。另有基于头像与模板的人物生成 | 作为国内服务优先核对账号可用性。官方已提示相关服务逐步迁往 TokenHub，原平台停止支持新购；新接入需确认实际入口及计费，不能沿用旧端点假定已开通。[产品与迁移说明](https://cloud.tencent.com/document/product/1804/120696) |
| Meshy | 多图接口接受同一物体 1 至 4 张图，可请求带纹理的 GLB；提供重拓扑及人物自动骨骼绑定 | 接口清楚，适合作为对照。自动绑定面向四肢清楚的标准双足人物，不是裙撑、假发或配饰的通用变形工具。[多图接口](https://docs.meshy.ai/en/api/multi-image-to-3d)、[骨骼接口](https://docs.meshy.ai/en/api/rigging) |
| Tripo | 官方多视图接口提供前、后、右等方向输入，并返回模型任务及 GLB 结果 | 作为另一组物品重建对照；固定 API 版本，避免把不同代模型与接口参数混用。[多视图接口](https://developers.tripo3d.ai/en/docs/generation-multiview-to-model/standard) |
| 自托管 Hunyuan3D 2.1 | 官方提供形状与 PBR 纹理生成代码及权重，说明形状约 10GB、纹理约 21GB、整体约 29GB 显存 | 可用于有合适 GPU 的离线研究；该基线不适合直接作为 Android 手机端生成功能。云端 3.1 与开源 2.1 的能力不能混称。[作者仓库](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1) |

以上支持生成三维资产，不等于已通过 Lolita 商品保真验收。就本项目而言，建议先比较鞋、包等轮廓清楚的物品，再加入硬腰封；蕾丝裙、细链条、透明薄纱、长卷发和裙撑另列样本。这个排序是按几何复杂度作出的工程判断，需要实物样本验证。

多视图必须是同一物品、同一款式和配色；不同配色不能当成同一物品的背面。AI 补出的侧背面应保留推测来源，不成为商品结构证据。Meshy 的 `auto_size` 明确使用视觉估计实际高度，不能把该值写成实测厘米。[尺度参数](https://docs.meshy.ai/en/api/multi-image-to-3d)

新建模服务使用自己的账号、密钥和计费，现有即梦与 OpenAI 生图配置不自动提供这些权限。初期宜先导入已有 GLB，确认资产本身有价值，再投入远端生成和长期运维。

## 个人模特与三维换装

### 可调人体

优先研究一个统一人体底模：固定拓扑、骨骼、基础姿态和 UV，使用形变目标调节体型；围度输入通过拟合并重新测量网格验证。身高体重只能约束部分信息，不能唯一决定胸腰臀与局部体型，缺失值仍为未知。

MakeHuman 与 MPFB 的核心素材标为 CC0，源码分别为 AGPL 与 GPL。可以先研究通过离线工具制作人体资产，再由 Android 加载资产；社区扩展、贴图及第三方头发另核对各自许可，不把素材许可与工具代码许可混为一谈。[官方许可](https://static.makehumancommunity.org/about/license.html)

SMPL 可作为参数人体与姿态的研究候选，但其可变形人体模型和导出的 SMPL-Body 是不同授权对象。官方 SMPL-Body 页面明确不包含体型形变及生成工具，不能依据输出网格的许可推定参数生成模型可直接用于应用。[官方区分](https://smpl.is.tue.mpg.de/license.html)

照片人物重建适合研究外观相似度，不能直接代替可调人体。衣服遮住的身体、单张照片不可见的背面及缺失围度仍缺少可靠约束；把现有二维模特转为 GLB，也不会自动生成统一拓扑、正确围度和可替换衣物。

### 独立物品与人体装配

建议按物品构造分开处理：

- 包、帽与部分硬配饰先尝试挂点和刚体变换，允许人工修正位置；接触、带子与遮挡仍需检查。
- 鞋履需要左右脚身份、脚型、鞋底与地面关系；假发需要头部贴合与发际线，发片不能自动替换为整顶假发。
- 软腰封需要沿躯干曲面变形，扣具等硬部件独立保形；裙装需要体型适配、内外层和裙撑体积处理。

统一坐标与姿态是资产接入约定；只有人体和衣服尺寸相容时，装配才有意义。简单把两份 GLB 放在同一个场景，常会出现比例错误、衣服悬空或穿插。

前面的[腰封部件原型](plans/2026-10-20-controlled-waist-parts.md)已经表明，可控制的变形与原部件保留有价值，但曲面、接缝和接触仍依赖手调。三维路线可把曲面、深度遮挡和不同视角纳入控制；扣具数量、纹理和材质是否正确，仍取决于资产如何制作。单张商品图缺失的厘米、硬度和背面不会因此自动补齐。

### 布料仿真

有真实版片、缝线和物性后，可研究 CLO 等专业工具在电脑或服务端完成穿衣与仿真，再导出手机展示资产。CLO 官方支持 GLTF、GLB 导出，并区分服装、人体及动画；导出格式支持不表示手机查看器获得了原求解器。[官方导出说明](https://support.clo3d.com/hc/en-us/articles/360051525034-glTF-2-0-GLTF-GLB-File)

首期可固定站姿，只展示已拟合好的组合。后续再比较预先制作的体型组合、运行时服装变形和服务端重新仿真的成本；连续调围度、多件即时换装、行走和布料动态不放入同一首期承诺。

## 接入应用时的数据与交互建议

先让三维资产作为物品或个人模特的可选附属资料，保留二维图片作为默认封面与回退。需要分别保存原始证据、AI 重建结果及人工制作模型，记录资产文件、SHA256、来源、生成版本、尺寸来源和验证状态；骨骼、体型及服装挂点按实际装配需求追加。

首期流程建议为：详情选择导入 GLB，完整预览并确认关联，后续从同一详情打开；替换和移除仅作用于所选资产，保留原图片。列表与选择器继续加载普通缩略图，只有用户打开查看器时加载三维场景。三维窗口支持旋转、缩放、重置和退出，小屏大字时主要操作仍可达。

现有图片读取器不能校验三维资源。应新增独立模型文件管理，统一私有存储、引用保护和备份屏障；图片缩略图继续沿用 `ImageFileHelper`。首期优先单文件内嵌 GLB，限制文件、贴图、顶点及纹理内存预算，避免模型打开后才发现无法在目标手机展示。

如新增持久实体，则实施 Room 增量迁移并完整接入 DAO、Repository、AppModule、StateFlow。备份同步覆盖 JSON 元数据、ZIP 模型字节及摘要、预览数量、路径重映射和适用 CSV；旧备份显式迁移为空资产集合，失败保全旧库与原文件。当前仅调研，不修改 Room 30 或备份格式 10。

远端建模宜采用独立的三维任务与结果协议，复用已有确认和后台任务经验。必须持久化远端任务 ID：重启后查询已提交任务与下载已有结果，要与再次提交收费生成区分。提交结果不明时保留不确定状态，不能因为本地超时而自动重复付费。历史输入和资产版本应冻结，参数人体本地调整本身不触发生图。

个人照片上传须有实际输入预览、服务与费用确认；人体参数调整优先在本地执行。远端结果下载并完整核验后再成为本地资产，过期下载链接不能成为唯一保存方式。人物三维模型及身体参数继续按私人资料处理，分享时由用户明确选择。

## 下一阶段验证

| 阶段 | 具体产出 | 继续条件 |
| --- | --- | --- |
| 本地查看 | 独立 Android 样例加载一个人体和两件独立物品，完成旋转、缩放与退出 | 核对现有工具链兼容、真实手机帧耗时与内存、后台暂停、反复进入退出的资源释放 |
| 资产与装配 | 统一人体站姿，鞋或包的装配，再加入可分离硬部件的腰封 | 正侧背面无明显穿插或悬空；比例、扣具、接触与纹理分别验收 |
| 照片建模对照 | 同一商品的单图与真实多图结果，统一渲染比较 | 与原图逐视角核对，保留未知背面；模型质量足以支持实际展示或装配 |
| 人体参数 | 一组有实测围度的体型拟合与网格测量结果 | 分别记录输入、拟合后尺寸和误差，证明可调范围，不能只看人像是否好看 |
| 正式功能 | 导入、确认、查看、替换、移除及错误恢复完整流程 | 先归档界面图与七皮肤浅暗效果，再实现、设备对照、迁移与备份验证 |
