# 数据完整性审计

本报告记录 2026 年 10 月 11 日修复前的审计证据，基线为含未提交改动的工作区、应用 2.37.0（74）、数据库 19 和 21 个实体。当前代码存在会丢失历史付款、价格、穿搭关联、图鉴和图片的路径，不能据此承诺升级或备份恢复无损。后续已实施修复，当前状态和验证结果见 [数据完整性修复记录](data-integrity-fix-2026-10-11.md)。

## 已复现的升级和恢复问题

## 代码确认的导入导出问题

以下问题由当前实现直接确认，尚未在 Android 设备上执行故障注入。

1. **P1 图片导入和数据库提交无法一起回滚。** `BackupManager.kt:254` 在数据库事务前替换整个 images 目录，`301` 行的条数校验在事务提交后才执行。如果进程在替换图片后终止，旧库仍引用原路径，但旧图片已经移走；如果提交后校验失败，图片回滚和数据库文件恢复也无法保证一致。重启没有恢复日志处理。应先验证备份，使用独立图片代际目录、持久阶段记录和可恢复的提交/清理协议。

2. **P1 缺图静默成功。** `exportToZip` 算出了 `missingImageCount` 却没有使用，写 ZIP 时文件再次消失也会跳过；`PreparedBackup.missingImageCount` 始终保持默认 0，ZIP 解析不检查 `zip://images/` 引用是否确实存在。导入成功后删除旧图片目录，使引用旧绝对路径的缺图无法找回。应逐引用检查、输出缺图清单和校验值；完整备份发生缺图应失败或明确降级，不能报“含图片”的完整成功。

3. **P1 旧备份默认值不完整。** `migrateJsonString` 仅补 styles/seasons/locations/sources、颜色和单图转换。Gson 反序列化不能依赖 Kotlin 构造参数默认值；旧 Item 缺少 priority/imageUrls、Category 缺少 group、OutfitLog 缺少 updatedAt 等情况可能得到 null/0，导致转换失败或时间戳变为 0。无 imageUrl 与 imageUrls 的旧记录也未补空列表。应明确区分历史缺失字段的合法默认值和损坏字段，完成版本化迁移后再验证，全部通过才允许清空现库。

4. **P1 无备份格式版本和未来版本拒绝。** `BackupData.appVersion` 固定默认 `1.0`，未写实际 2.37.0、schemaVersion 或 formatVersion。Gson 会忽略未知字段；导入新增字段/实体的未来备份可能成功却永久丢掉未知数据。应增加格式版本、迁移链和支持范围，拒绝不支持的未来格式，不能只用应用显示版本作格式版本。

5. **P1 日历在导入成功前被删除。** `BackupManager.kt:258` 先删除现有付款日历事件，随后数据库备份或 SQL 失败不能恢复事件。成功后又给所有未来未付记录建立事件，未检查 reminderSet，改变了未开启提醒用户的行为。应在数据提交后按用户设置重建；失败时保留旧事件；权限失败独立提示并可重试。

6. **P1 旧闹钟未完整取消。** 导入后取消的是新库 payment ID，而非替换前的全部 ID。旧库有 ID=100、新库没有该 ID 时，旧闹钟会遗留；提醒接收器的最终用户影响需设备验证。应在成功提交后取消旧 ID 集合，再为新库重建，失败时保留旧提醒。

7. **P1 CSV 导出丢字段且没有一致性快照。** `exportToCsv` 未导出 Item 的 locationId/source/coordinateOrder、Category.group、Price.createdAt、Payment.createdAt、OutfitLog.updatedAt；多个 DAO 查询未包事务，导出期间修改可得到跨时刻引用。CSV 无导入入口，本来就不能用于全量恢复；应明确用途并补列，一致快照导出。JSON 只保存路径，也不能独立恢复跨设备图片。

8. **P1 远程库备份边界不一致。** 当前 21 个实体中 BackupData 只覆盖 12 个本地业务实体；导入 clearAllTables 会清空其余 9 个同步状态/远程实体却不恢复。若它们全是可重建缓存可作为显式例外，但当前 UI 没有呈现这个边界。历史 Schema 18 的两种图鉴实体也不在当前备份中。全量备份必须声明并校验表覆盖范围；用户数据不可归为缓存。

9. **P1 验证不足且有静默转换。** 导入只在事务外比较 Item 条数；没有比较其他表、业务字段、图片和外键全图。`ensureColorArray` 遇到无法解析的数组字符串会清空；`Converters.toStringList` 解析错误返回空列表，枚举转换也会回退。这些路径可能把损坏数据转换成看似正常的数据。应让预检查报告原值与错误路径，不将损坏值作为合法空数据接受。未知字段/枚举也应纳入拒绝或隔离策略。

## 次要风险和需要进一步验证的场景

- ZIP 根据文件名兼容旧绝对路径；旧 ZIP 中不同目录的同名文件落入同一暂存文件，会覆盖并映射为同一图片。新 ZIP 使用路径哈希文件名改善了正常情况，但解析器仍允许重复条目。应拒绝歧义和重复条目。
- `prepareBackup` 以 URI 缓存预览内容，源文件发生变化不会重新读取；锁仅保护缓存赋值，不保护整次预览/导入。并发操作可清掉另一个操作的暂存目录。应串行执行恢复，并绑定不可变备份内容或哈希。
- 图片替换会删除所有旧图片，而备份未覆盖的实体可能仍需要它们。共享图片路径的记录删除也未做引用检查；从旧备份恢复的共用路径尤其需要验证。
- `PaymentRepository.updatePayment` 在 DAO 更新前删除旧日历/插入新日历，数据库更新失败会造成外部状态与数据库不一致。
- `LolitaApplication` 每次启动都刷新 OWNED→PENDING_BALANCE，备份恢复后启动状态可能发生变化。此类派生字段允许转换必须有明确规则；历史无尾款的 PENDING_BALANCE 是否反向修正需业务定义。

## 修复顺序与验证结果

优先保全历史迁移的引用图与图鉴数据，其次取消不安全的在线主库文件回滚，实现数据库和图片的可恢复提交，再补版本化备份、旧字段默认值、缺图检测与导出覆盖，最后处理提醒及并发。

`./gradlew assembleDebug` 已通过。临时 SQLite 的四项数据保留检查失败，证据见复现脚本输出。ADB 当前无连接设备；Room 仪器化迁移、实际导入、杀进程和跨设备恢复尚未执行。现有 USB G13 仅打开文件选择器后返回，不能证明恢复无损。
