# 升级与备份数据完整性测试用例

目标是证明旧版本覆盖升级、旧备份导入、新版本往返备份以及失败恢复时，用户数据和图片完整。历史已购、购买证据与未知日期付款的最新规则及已执行用例见 [历史购买修复](historical-purchase-fix-2026-10-11.md)。本方案是完整验收范围；已执行的自动回归及仍需验证的项目见 [修复记录](data-integrity-fix-2026-10-11.md)，不能将部分自动回归当作全套测试通过。

## 测试环境与备份边界

记录旧/新 APK 的 versionCode、versionName、SHA256、数据库 user_version、Schema identityHash、Android 版本与设备。当前新代码数据库版本为 23，完整备份格式为 5；旧版本使用实际发布 APK，不用改 versionCode 冒充旧包。覆盖 API 26、当前常用设备系统；导出使用 MediaStore.Downloads，还应单独验证 API 26/28 是否具备有效输出路径。Release 测试包用 `clean assembleRelease` 构建，升级包必须同 applicationId 与签名。

只在专用测试设备或模拟器操作。测试库、图片和日历必须与真实个人数据隔离。备份固定在测试设备外，禁止只把唯一副本放在将被替换的 filesDir 内。升级使用 `adb install -r`，保留应用数据；恢复到空库使用另一台干净测试设备，避免卸载和清数据影响升级证明。

建立表覆盖清单：当前本地业务包含 legacy_catalog_archive、order_bindings、payment_stages 与 brands/categories/coordinates/items/prices/payments/outfit_logs/outfit_item_cross_ref/styles/seasons/locations/sources；完整 JSON/ZIP 还覆盖 SharedLibrarySyncState 和 Remote 缓存，RestoreJournal 仅为本机操作日志。历史版本另有 catalog_entries；同步状态和 Remote 表逐表声明是否为可重建缓存。任何要废弃的用户实体都需要可校验的归档和恢复目的地，不能作为允许删除的例外。JSON 不包含图片字节，CSV 当前无恢复功能；只有完整 ZIP 可承担独立全量备份验收，其他格式按其明确边界单独验收。

## 固定数据集和比较规则

使用独立的基准清单，不能只用被测 BackupManager 的导出结果作为 oracle，否则导出和导入共同漏掉同一字段仍会通过。基准由受控测试夹具和数据库查询产生。

| 数据组 | 固定样本 |
| --- | --- |
| 属性 | 各 2 个自定义品牌、分类、风格、季节、来源；分类含不同 group；名称有中文、emoji、引号、逗号、换行。两个位置、两个套装。 |
| 服饰 | 6 条，覆盖全部实际 ItemStatus/ItemPriority；普通拥有、愿望、未付尾款、全付尾款；关联位置/套装及空关联；多颜色、多季节、来源、尺码、尺码表和 coordinateOrder=7。 |
| 价格和付款 | 4 个价格：全款、定金尾款、0 金额、多个付款记录；至少 7 个付款，含已付、未来未付、逾期、reminderSet=true/false、customReminderDays=null/0/3；金额 0、0.01、1234.56。 |
| 穿搭 | 3 个日志、4 条跨表关联；空图、单图、多图，两个日志引用同一服饰；非零且不同的 createdAt/updatedAt。 |
| 图鉴和同步 | v16/v17/v18 各含独立图鉴和 linked_item_id 图鉴。远程表每表至少 1 条；保留目标或缓存例外逐表记录。 |
| 图片 | 品牌 logo、服饰多图、尺码表、套装图、穿搭图、位置图；两张不同内容同名不同目录图片；两个记录共享同一路径；文件名含中文；空图片列表。记录字节 SHA256、大小及引用位置和顺序。 |
| 标识和时间 | 主键非连续如 101/307/9001，大 ID；所有外键显式记录。时间戳固定并包含月底和跨年边界，不用运行时间作预期值。 |

数据库以主键排序、逐字段比较；关联以复合主键排序。图片列表顺序和重复引用关系也必须保留，路径跨设备可变，比较每个引用指向的字节 SHA256。金钱逐记录核对并用十进制汇总，避免只依赖 Double 汇总误差。检查每条付款和价格的父记录、每条穿搭关联以及旧图鉴链接；执行 `PRAGMA integrity_check`（仅 ok）与 `PRAGMA foreign_key_check`（零行），但这两项无法发现被级联正常删除的记录，必须额外比较内容。

允许变化仅限精确列出的字段：backupDate、备份版本元数据、设备图片绝对路径、系统 calendarEventId，以及经过定义并可重复验证的派生状态。createdAt/updatedAt、业务日期、金额、属性、排序与主键不得一概排除。历史新增字段必须给出明确默认值；未知字段或未来版本不能被静默丢弃。

## 测试执行与发布门槛

1. 先运行 `python3 scripts/audit_data_integrity.py` 获取当前缺陷证据。脚本以数据保留断言检查迁移与保护辅助流程，发现丢失时返回 1；它仅覆盖两段重建迁移、删图鉴和 WAL 主文件复制，不能代替上表。
2. 为 U02～U05 接入 `androidx.room:room-testing`、AndroidJUnitRunner 与历史 Schema 资源，建立可执行仪器化测试。当前已接入 BackupFormatTest 和 DataIntegrityTest，迁移覆盖 2～22→23（20/21→22 的购买证据回归位于 HistoricalPurchaseTest，22→23 及归档证据回归位于 PersistentOrderEvidenceTest），数据库版本 1 仍需真实发布夹具补充。
3. 每个旧 APK 先生成夹具和独立基准，在设备外保存原始 ZIP、数据库一致快照和图片哈希。数据库快照通过 SQLite backup 或明确停机且正确处理 WAL 获取，不直接复制在线主文件。
4. 执行所有 P0/P1 用例，并保存独立核对结果；UI 套件 `bash run_device_test.sh` 只作为额外冒烟验证，G13 不能代替导入后校验。
5. 新包编译通过；迁移与备份所有关键用例零丢失、零错链、零错误图片；所有故障用例恢复完整 A/B；未来版本拒绝有效。缺图、表消失、静默默认值或未执行关键用例都不得签署无损结论。
