# 历史已购与付款资料缺失修复

历史服饰的购买状态不能仅由缺失的付款记录推导。旧订单迁移曾把已购但没有付款记录的价格绑定为当前订单，随后按已付零元覆盖为待付款；旧 v1 导入和 13→14 升级还曾凭已拥有状态生成满额实付。两条推断均已修正。

## 数据与交互

- Room schema 22，完整备份格式 4。`OrderBinding.purchaseRecordStatus` 保存 `TRACKED`、`HISTORICAL_OWNED`、`NEEDS_REVIEW`，默认为新订单的 `TRACKED`。
- 历史原状态明确为 `OWNED`、但实付资料不足的订单保留已拥有，不补造金额和日期。已升级 21 且原状态丢失的空账本标为 `NEEDS_REVIEW`，服饰显示待核对；有真实计划的新待付款订单继续按正常账本计算。
- 价格页提供“确认历史已购”和“确认仍待付款”。零实付的正常账本也提供手动历史纠正入口。确认更新证据及状态，保留价格、阶段和所有原付款。
- 历史已购的价格、阶段只读，可补录/更正能够确认的真实付款；新补录的历史日期为空，用户须选择实际付款日期或明确勾选“付款日期记不清”。未知日期实付计入消费总额与分布，不归入年/月趋势。未付余额显示未知，补录上限只是资料校验上限。
- 欠款、逾期、日历计划与提醒仅使用 `TRACKED`；提醒接收器也检查证据标记，忽略过时闹钟。消费分布和趋势只使用已保存的实际付款，未知资料不变成消费。
- 21→22 和旧备份显式迁移保全原始记录。新版 JSON/ZIP、CSV 和恢复预览同步保存/展示标记；原始未知枚举、无效金额仍拒绝，不能以历史标记绕过校验。

## 回归

`assembleDebug testDebugUnitTest assembleDebugAndroidTest` 通过，49 个单元测试零失败。独立 API 35 模拟器运行历史购买 13 项、订单业务 12 项、数据完整性 8 项、统计 4 项，共 37 个设备用例通过。覆盖 20/21→22、原已购且只有旧计划/部分实付、状态确认、正常新欠款、归档再绑定、显式历史日期与日期未知选择、付款修改、空数据快速维度切换、价格开关、超额校验、参考金额不自动入账、备份恢复及账目和图片保全。

独立模拟器通过正式恢复界面重新导入仓库原始 `lolita_backup_20260318_191642.zip`，逐字段验证 1,003 条记录、8,699 个字段和 190 张图片 SHA256。15 个历史已购订单没有生成付款；124 个正常账本、15 个历史已购标记正确，真实实付为 133 笔、¥52,717.37。

已经由旧程序生成的付款不能仅凭时间/金额模式自动删除，因为合法原始付款也可能相同。测试库有原始 ZIP 的逐字段来源证据，可通过正式重新恢复纠正；其他用户的既有库保留全部原付款，缺失购买证据时由用户核对确认。

## 历史付款补录

补录页展示现有服饰、来源、订单总价、已录实付和保留的淘宝订单说明。用户可以点击“填入参考金额”获取可编辑参考，只有核对真实实付并保存后才写入付款，不因已购状态自动生成记录。

`recordHistoricalPayment` 仅接受当前绑定为 `HISTORICAL_OWNED` 的订单；日期未知保存为 `paidDate=null`，旧必填 `dueDate` 使用 0 占位。正常新付款仍要求实际日期，编辑原本日期未知的实付允许继续保留 null。所有金额、阶段、超额与重复录入的账本约束不变，补录、编辑、撤销均保留历史已购证据。

原始 ZIP 的 15 个缺付款订单仅保留价格，商品描述与来源为空，没有购买日期或订单号。不能从两批数据库创建时间恢复实际付款日。仓库的淘宝 Excel 是另一来源，需按源订单逐项核对；其时间列为订单提交时间，不能自动当作付款时间。
