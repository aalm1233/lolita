# 服饰部件与付款管理改造方案

每件独立计价的服饰只有一笔订单价格，付款可以分多段。裙子可以包含小物，小物可以包含在主件价格中，也可以独立计价。付清表示已收到、已拥有，未付清表示未收到。首版已在 2.38.0（76）、数据库 21 中实现；验证记录见 [实现与回归记录](../item-pricing-implementation-2026-10-11.md)。

## 已确定的规则

- 一件服饰最多有一笔有效订单价格。定金、尾款、邮费和分期不能作为重复的服饰价格录入。
- 商品金额和邮费分别维护；订单应付总额等于商品金额加邮费。付款阶段只是拆分这笔应付总额，不能再次加到总额上。
- 每笔实际付款单独保存金额和实际付款日期。修改订单金额或阶段到期日，不改变历史实付。
- 付清对应已拥有，未付清对应待付款。明确的定金尾款计划使用待补尾款文案；全款未付和普通多段付款使用待付款。愿望单表示尚未购买。
- 无价格表示尚未录入或共用主件价格，不能一律按零元且付清处理。包含在主件价格中的小物不再重复贡献价格。
- 共用价格的小物继承主件付款状态；独立计价的小物按自己的付款判断。用户已确认此规则。

## 服饰与部件

保留现有套装分组 Coordinate，新增主件和部件关系。现有套装没有足够信息确定哪一件是主裙，迁移时不自动推断。Item 继续保留独立 ID、图片、尺寸、分类、位置和穿搭引用。

首版支持一层主件与部件关系，禁止自挂、循环关系和把同一小物同时挂在多个主件下面。主件可以是裙子，也可以是其他服饰。部件独立计价与挂载关系分开维护。

| 形式 | 价格入口 | 状态计算 | 费用统计 |
| --- | --- | --- | --- |
| 独立服饰 | 自己的唯一订单 | 自己的实付与应付比较 | 自己的订单计一次 |
| 包含在主件价格中的小物 | 展示包含于主件价格并可查看主件订单 | 继承主件状态 | 不增加费用 |
| 单独计价的小物 | 自己的唯一订单 | 按自己的订单判断 | 独立订单计一次 |

组合汇总可以显示所有独立订单，但不能用组合总额覆盖主件自身价格。

例如裙子商品金额 1000 元、邮费 20 元，发带和胸针包含在裙子价格中，另购腰带 80 元。主件订单应付 1020 元，组合应付 1100 元；发带和胸针不能各自再展示 1020 元并参加累加。裙子付清后，裙子、发带和胸针已拥有；腰带按自己的付款判断。

## 订单和付款

使用三个明确的业务对象：

| 对象 | 内容 | 约束 |
| --- | --- | --- |
| 订单价格 | 服饰 ID、商品金额、邮费、应付总额 | 每个独立计价 Item 最多一笔有效订单 |
| 付款阶段 | 名称、类型、应付金额、可空的到期日期、排序、提醒设置 | 全款、定金尾款或任意多段，完整计划的阶段应付合计与订单一致 |
| 实际付款 | 实付金额、实付日期、关联订单和可选阶段 | 支持阶段部分付款，保留完整历史 |

首版继续保留历史 Double 存储值，计算与比较转换为整数分，新输入限制两位小数并检查范围。邮费由用户确认，零邮费有效；淘宝导入的建议分配须逐项确认才能入账。未来可考虑整数分存储及未知邮费的独立状态。

未付余额根据订单总额减实际付款合计计算，不能根据剩余未付款记录的数量判断是否付清。新增、修改、撤销付款，调整价格、邮费或计价关系时，都在同一数据库事务内刷新受影响的状态。提醒和日历事件在事务成功后同步，失败可重试。

新输入不允许负金额或无意超付。历史超付不能被裁剪，应保留并标记异常。退款与订单取消应作为后续明确的记录类型设计，不用负付款隐式表示。未知尾款日期可以留空，此时不安排到期提醒，也不制造当天逾期。

## 页面变化

- 价格管理改为价格与付款。没有订单时显示设置价格；已有订单显示编辑价格，不再显示添加第二笔价格的悬浮加号。
- 订单页面展示商品金额、邮费、应付总额、实际已付、未付余额。全款、定金尾款和多段付款作为计划模板。
- 加号用于添加付款阶段或记录实际付款，两种操作明确区分。每段分别展示应付金额、实际已付、到期日及提醒。
- 主件详情新增所属小物分区，可新增小物或从已有服饰挂载，挂载时选择包含在主件价格中或独立计价。
- 服饰列表默认展示主件，显示小物数量并从详情查看；搜索、分类筛选和穿搭选择仍能找到独立小物。套装分组保留。
- 部件详情展示所属主件与计价方式。解绑、换主件和切换计价方式不能删除实付记录。已有独立订单切换为共用价格时先处理原订单，不能静默清空。
- 删除主件前必须处理部件归属与账目；首版采用引用限制，避免级联删除部件和付款历史。

## 历史数据与备份

迁移保留所有服饰和付款 ID，不合并服饰实体，不更改穿搭记录。只有一笔历史价格的服饰可以映射到一个订单；多笔价格的含义无法从现有字段确定，必须保留所有原始价格与付款，提供待核对列表，不能自动求和或只保留最新一条。

通过当前订单绑定实现唯一性：以 itemId 为主键，绑定一个有效 priceId，保留原价格表和付款表作为历史来源。没有直接给历史价格表增加 itemId 唯一索引。只有一笔有效旧价格时自动绑定；多笔旧价格、异常金额和无实付证据的愿望单预算价等待核对。待核对金额单独展示，不能隐式按零处理，也不能混入已经核实的消费。

历史定金与尾款 Payment 没有阶段身份，无法可靠地按金额或顺序推断；不能仅因为金额相同就去重。迁移逐条建立“历史付款 ID”阶段，完整保留原始记录；旧未付行只作原始计划，不计入实际支出。超付和计划不平衡项展示核对提示，由用户选择正确的订单及计划。无价格的旧服饰保留状态，不能按零元付清处理。极旧数据的可选购买日期为空时，已拥有记录仅保留历史已购证据，不能凭已收货状态、价格或创建日期生成实付。此历史规则已由 [历史购买修复](../historical-purchase-fix-2026-10-11.md) 更新：购买证据不足的订单待核对；金额已确认但付款日期记不清时，由用户明确补录日期未知的真实付款。

新增订单、阶段、实付和部件字段必须同步 JSON 导出、ZIP 图片导出、导入、预览和 CSV 列。旧备份导入复用同一套迁移策略。共用价格导入须验证主件存在、禁止循环、计价方式与订单归属一致。未来版本或不支持的字段继续拒绝导入，避免静默丢失。

淘宝导入改造需处理已解析但未记账的邮费、订单实付和数量。一个淘宝订单有多件独立商品时，邮费属于订单一次费用，不能对每件商品重复加完整邮费；保留来源订单编号并在预览中核对分配。识别到套装也不应仅凭商品名称自动吞掉部件。

统计按实际付款日期计算支出，包含未收货订单已付的定金。日期未知的历史实付计入总支出，不进入年月统计或付款日历。待付款统计仅按完整账本的余额计算；历史已购保留已拥有，付款资料待核对不算欠款。组合、套装及列表汇总按订单 ID 去重，不重复累加共用价格的小物。商品价格统计与实际支出明确区分。

## 改造顺序

1. 订单与账目模型、事务联动及历史冲突核对，解决重复记账和日期误标付款。
2. 唯一价格入口、邮费、多段付款页面和提醒。
3. 主件与部件挂载、独立或共用价格、详情和列表展示。
4. 导入、统计、备份兼容、完整迁移及设备回归验证。

数据库结构变更需要新版本及迁移，发布前必须从已提交源码执行 clean assembleRelease。旧版本备份在新版本导入和再次导出后，账目、关系、图片及原始异常记录均须可核对。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 同一服饰重复设置价格或并发保存 | 最多一个有效订单，不能产生双份价格 |
| 定金 300 加尾款 700，总价改为 1100 | 原实付仍为 300，余额为 800，不重复生成已付定金 |
| 修改定金日期 | 尾款实付与收货状态不被误改 |
| 删除尚未付款的尾款阶段 | 余额仍未付清，不能变成已拥有 |
| 商品 1000 加邮费 20，多段支付 300、700、20 | 实付 1020 后变为已拥有，邮费只记一次 |
| 尾款日期未知 | 保留未付余额，不制造到期日或逾期提醒 |
| 一个阶段分两次付款 | 两笔实付完整保留，阶段与订单余额正确 |
| 主件与两个共用价格小物 | 费用只统计一次，状态同步 |
| 主件与独立计价小物 | 挂载不重复统计，付款状态分别计算 |
| 主件更换、解绑或删除 | 部件与账目完整保留，没有循环引用 |
| 历史多价格、相同金额付款和超付 | 无静默删除、求和、裁剪或推断去重，可核对原始数据 |
| 旧备份导入后重新导出并恢复 | 账目、图片、穿搭及部件关系一致 |
| 数据库更新失败或提醒同步失败 | 数据事务回滚或提醒重试，不残留半套账目 |
| 跨月付款及共用邮费的淘宝订单 | 统计按实际日期，邮费及订单金额不重复 |
