# 第三轮功能体验：淘宝订单导入与后续整理

日期：2026-10-22。状态：**体验审查与优化建议，未实现**。

本轮承接2.67.0的两轮设计实施，回答“还有哪些功能值得优化”。优先建议改善订单导入的可靠性、续办和批量整理；已完成的实验室、空态、备份及价格保存栏不重复列为待办。

## 体验范围与证据

- 基线：源码 `d1ecd452`，其中应用源码与正式2.67.0 / 142相同；体验使用独立 `Lolita_Creative_Test_35`（emulator-5602）中的2.67.0 Debug包，通过真实文件选择器和Compose页面操作。
- 默认1080×2400、420dpi、fontScale 1.0；追加实际960×2100、480dpi（320dp宽）、fontScale 2.0。结束后恢复原尺寸、密度与字号。
- 文件为本轮构造的虚构订单：6笔订单、6个商品行、7个实体件；其中一行数量2，另含定金、尾款、关闭订单和类型待确认项。默认选择5行，进入核对得到6条资料。
- 真实走查：文件选择、默认勾选、品牌准备、数量拆分、逐件金额核对、部分导入、完成退出、同文件重复导入、无法解析金额、后台进程终止后重入、多文件同订单金额冲突、小屏大字。
- 重复导入测试仅在独立AVD创建2条同源虚构物品和1个虚构品牌，保留现场；不操作用户设备或真实订单。不调用淘宝账号、不上传资料、不发起付费AI。
- 附件见[证据清单](../visuals/2026-10-22-order-import-review/evidence.json)。原始截图、UI树、三份测试文件及设备记录按原字节归档；截图不是设计稿。
- 未改应用代码、数据库结构或版本，不重跑无关测试、不构建发布。本轮未验证真实淘宝账号的导出入口、线上格式变化、全部七皮肤或TalkBack。

## 最优先的五项

### 1. 同一件可以重复导入，需建立跨批次识别

**实测**：首次只确认 `REVIEW-001` 的第1/2件，成功新增1件；完成后重新选择同一文件，再确认同一件，个人页数量变为2。数据库两条记录的来源均为“原行1、件号1/2”，`import_token`均为空，不是正常的第1件和第2件分别保存。

**根因**：`TaobaoOrderParser.parseMultipleFiles()`仅在当次文件集合中按订单号 `distinctBy`；`executeImport()`新建Item没有持久化可供订单导入查重的结构化标识。既有商品链接导入的importToken保护不能自动覆盖该路径。

**建议**：导入预检区分“新资料 / 已导入 / 来源有变化 / 无法确定”。已导入项默认不再新建，允许查看原物品；冲突先比较来源快照再确认。使用明确的来源身份与导入记录，同事务保存结果映射；不能只凭商品名称、文件名或可能变化的行号自动合并。历史描述文本只能作为候选证据，不能静默回填为确定身份或删除已有重复项。

**验收**：同文件重读、导出顺序变化、同款不同尺码、同单数量2、配对两笔订单、提交成功但结果未回显后重入，均不重复记物品或实付。恢复旧备份后不把无标识历史项误判为新资料。

证据：[重复选择](../visuals/2026-10-22-order-import-review/08-repeat-selection.png)、[再次成功](../visuals/2026-10-22-order-import-review/09-repeat-result.png)、[数量变为2](../visuals/2026-10-22-order-import-review/10-repeat-count.png)、[同源记录](../visuals/2026-10-22-order-import-review/duplicate-records.json)。

### 2. 金额解析失败被变成0，且同订单不同金额被直接去重

**实测**：测试文件商品金额及实付写为“待确认”，页面显示“源金额¥0.0、源实付¥0.0”。勾选已核对后仍为0/1可导入，没有就地说明被哪个条件阻止。此样本未写入数据库：现有总金额大于0校验挡住了提交，不能据此宣称错误零金额已经入账。

另将同一订单实付分别写为310元和299元，同时选择两份文件，页面仅提示去重1笔，没有提供金额冲突比较。

**根因**：`parsePrice()`失败回退0.0；前11列按固定位置读取，未核验必需列名；同订单号直接保留先读到的版本，不比较金额、状态和商品行。

**建议**：文件预检保留原值，分别表达“有效0 / 空白 / 格式不识别”；显示文件、行、字段和修复动作。多个来源完全一致才合并，资料不同则进入冲突核对。首阶段校验表头和必要列；多文件失败明确指出哪份文件，保留其他已读文件状态，不能无说明地接收部分订单。

**验收**：空白、人民币符号、文本、负数、非有限值、表头移动/缺失、订单号格式异常及多文件冲突；未知金额不能显示成免费或已付0。修改本件金额后重新计算校验，但不改写源证据。

证据：[零金额及无原因的禁用状态](../visuals/2026-10-22-order-import-review/13-zero-blocked-no-reason.png)、[冲突被去重](../visuals/2026-10-22-order-import-review/18-conflict-dedup.png)。

### 3. 导入草稿与剩余项需要可续办

**实测**：导入1件、跳过5条资料后，结果页只有“完成”；没有继续剩余项、查看本次物品或失败原因清单。进入核对后将应用置于后台，执行Android `am kill`，确认原进程已消失；再次启动回到选文件页，未恢复核对内容。

**根因**：订单导入依赖 `MutableStateFlow`，没有持久导入会话；结果只保留三个数量，未保留本次写入ID和逐项状态。编辑页返回已有放弃确认，但不能解决后台回收和导入后剩余资料的继续处理。

**建议**：本机保存导入会话、原始证据、未完成输入、配对和图片引用；页面重入显示“继续上次导入”。结果页提供“查看本次新增”“继续核对剩余5条”。已提交项从待办中剔除，保持已提交ID可追溯；离页不自动执行剩余导入。现有物品编辑的草稿经验可复用，但订单批次需要独立提交状态，不能把所有数据塞进SavedState。

**验收**：旋转、切底栏、后台回收、提交前后进程终止、部分完成后退出；不丢输入、不重复提交、不误清理已保存或未完成项图片。

证据：[部分完成](../visuals/2026-10-22-order-import-review/07-partial-result.png)、[进程终止后入口](../visuals/2026-10-22-order-import-review/14-after-process-death.png)、[进程记录](../visuals/2026-10-22-order-import-review/process-death.json)。

### 4. 先解决真实小屏大字下的订单可读性

**实测**：320dp / 两倍字体的选择页，310.00元被挤成多行竖排；店铺与日期占用同一行大部分宽度，“全选”未在可见页面中出现。逐件页固定操作区明显挤占正文高度。

**建议**：摘要、选择操作分行；店铺/日期和金额采用响应式纵向布局，金额保持完整可读。核对页将进度与剩余原因收敛为紧凑摘要，大字时优先通栏输入；上下件和主按钮保持可达。保留四个底栏入口和现有皮肤身份，不压缩系统字号。

**验收**：七皮肤浅暗的默认与320dp/2.0字体；长店铺、时间、金额和标题，真实键盘以及选择0/多条，不能仅断言控件存在。

证据：[选择页](../visuals/2026-10-22-order-import-review/15-small-selection.png)、[逐件页](../visuals/2026-10-22-order-import-review/16-small-detail.png)。

### 5. 用“待处理原因”驱动核对，降低逐件翻找

**已确认现状**：已有逐件/批量切换、全款/定金/尾款/待配对过滤、金额核对复选框、相邻配对排序。不要重新开发这些能力。

仍缺少“缺类型、金额异常、日期待核对、尚未确认”等明确原因，以及“下一条待处理”。当前“批量编辑”主要是多张编辑卡依次展示，并不提供多选后统一修改属性。

**建议**：顶部显示可导入和待处理数量；点击原因进入相应条目与字段；主卡给出本件尚缺什么。增加下一条待处理，保留原始索引与配对关系。对明确选中的物品可提供批量设品牌/类型等动作，显示影响范围；金额、实付与付款日期继续逐项核对，避免一次勾选掩盖错误。

## 第二优先级：减少选择和重复录入

| 现状 | 优化方向 | 边界 |
| --- | --- | --- |
| 初始订单列表只有全选，没有名称、店铺、日期或状态筛选 | 增加搜索、店铺/时间范围/状态筛选及“只看已选”；筛选保留隐藏选择 | 默认保留现有成功订单选择规则，关闭/退款状态继续明确核对，不自动当零实付 |

| 准备页仅提供创建或跳过缺失品牌 | 每个店铺可选择已有品牌、新建或保持未设置；就地搜索并展示匹配依据 | 不凭近似名称自动合并真实品牌；既有已核验别名匹配保留 |

| 商品图片仅能本地选择；订单原商品链接只用于配对，写入Item时未保留 | 保留公开来源链接，提供“补全本件商品资料”，选择更新名称/规格/图片并预览差异 | 必须绑定现有物品，避免再造一件；不自动抓账号、不自动调用AI，保留原图和人工修改 |
| 文件加载后缺少追加/重新选择入口 | 显示文件名、解析状态和追加文件；替换时明确处理当前草稿 | 复用原会话和来源识别，不静默清空编辑或重新计算已确认的账目 |

## 其他值得衔接的现有功能

以下基于相关入口和代码检查，未做独立完整设备验收，属于下一轮候选范围。

1. **购买资料核对清单**：现有 `FilteredItemListScreen` 已显示原因，但主要是平铺列表、进入详情再处理。可按缺价格、缺真实付款、缺日期分组，并直达相应核对动作；提供“下一条”。不能一键把历史未知账本改为已付清。
2. **导入后整理收纳**：房间页已经支持搜索和多选移动；应从导入结果带本次新增ID进入既有选择流程，减少重新寻找，不重建另一套移动功能。仅已拥有物品可分配位置，待付款和心愿保持原规则。
3. **订单与商品链接导入衔接**：订单负责购买证据，商品页负责图片与规格。通过明确绑定现有物品完成资料补全，保留字段来源和用户选择，避免两个入口分别生成重复物品。已存在的物品草稿、图片完整展示及来源保护应继续复用。

## 建议的改造顺序

第一批：来源查重与冲突核对、金额解析异常、导入草稿、剩余项续办。四者共享会话与来源模型，需一并明确数据提交与恢复策略。小屏金额阅读问题可先作为独立布局修复。

第二批：订单搜索筛选、准确数量、按原因核对、品牌映射、日期输入和紧凑布局，保留已认可的逐件卡片与定金尾款排序。

第三批：本次新增清单、批量收纳、原链接补图以及购买资料核对的连续处理。

建议主流程为：**选择订单 → 处理待核对 → 导入结果 → 继续剩余 / 查看本次物品**。导入草稿是各阶段的恢复入口。

本轮只确认问题与优先级。正式实施前按规范归档可审阅界面稿、七皮肤浅暗效果、小屏/键盘方案；当前真实截图不能充当前置设计稿。

## 后续设计必须保留的业务规则

- 现有整数分分摊、付款类型纠正、合法双向配对及相邻展示、整批事务、原金额证据和完成后提醒协调继续保留。优化效率不降低实际付款核对要求。
- Room32 / 备份13本轮未变。如果持久化导入会话或来源实体，实施时评估迁移与备份导出/导入/预览，兼容无来源字段的旧备份；恢复后不能自动执行未完成导入。
- 会话图片通过ImageFileHelper和引用保护管理，缩略与完整Fit预览分开；原图不因失败、返回或处理剩余项而被误删。
- 金额隐私沿当前规则检查；来源文件与草稿留本机，公开报告只使用虚构资料。商品页读取和AI是明确的额外操作，不能由恢复草稿触发网络或计费。
- 来源身份必须处理行序变化、数量与配对；禁止通过猜测自动合并历史物品或改写已记账实付。
