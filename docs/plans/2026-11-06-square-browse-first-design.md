# 广场先逛选，再加入心愿 · 2026-11-06

状态：前置图稿已获用户确认并按本方案实施2.74.0；原生验收与最终差异见[实施记录](../square-browse-implementation-2026-11-06.md)。本文件保留设计阶段依据，HTML图稿不代替原生验收。主助手未访问淘宝。

## 采用的产品方向

广场的第一任务是让人逛店选品：看到商品、看清图片、切换喜欢的单品与颜色、了解参数，喜欢便加入现有心愿单。用户表达心愿时，可以还没决定尺码，也可以暂时不知道小物的材质。

采用流程为：**广场图片卡 → 商品详情看图与参数 → 加入心愿 → 留在原处继续看；需要时查看已有心愿物品。** 单品资料整理服务于后续管理，不能成为表达心愿之前的必修步骤。

本轮取代 2.73.1 的默认四步登记路线。保留它对真实部件、原图、组合身份、未知值与账本的正确边界，取消默认要求用户先处理完整 SKU、拆分、逐件选图、预览和完整编辑的交互。已保存物品、草稿及原有导入功能不据此自动迁移或重写。

不扩展账号、关注、推荐算法、在线内容服务、评论、购物车、支付、自动采集或每日监测。当前资料仍为本地公开目录，不承诺实时库存或绝对最新。

## 现状判断与证据

审查依据为 `SquareScreen.kt`、`SquareRegistrationScreen.kt`、`SquareViewModel.kt`、`SquareRepository.kt`、`data/square/` 模型、现有 Item/ItemDraft/来源及图片保存实现，并对照 [2.73.1 实施记录](../square-refinement-implementation-2026-11-06.md)与[已发布真实商品页](../visuals/2026-11-06-square-refinement/native/release-product.png)。

真实页面第一屏依次排了店铺、系列名称、状态日期、采集说明、切换商品链接和部件资料目录。JSK、KC、内搭各有小图，但整张商品图还在下方，部件本身也不是能切换当前商品视图的选择器。用户看到的是一份待整理的目录。

代码中的主按钮为“选择规格，加入衣橱”。按下后是选择完整规格、拆出我的物品、挑选对应资料、登记预览，再逐件进入完整编辑器。其数据保护已经成立，但默认流程的动作目标变成了资料登记。`SquareDetail` 中切换 `chosenProduct` 只切来源商品链接；`role` 切的是主图/规格/详情/促销的技术图片类别。二者都不能直接回答“我想看看蓝色 JSK，再看看对应 KC”。

问题因此不是再缩几个间距或改一个标题，而是浏览对象、视觉主角与提交结果同时错位。

| 2.73.1 当前行为 | 本轮采用行为 |
| --- | --- |
| 动态与商品链接组织详情 | 系列作为入口，当前单品/颜色组织看图与参数 |
| 部件目录先于完整商品图 | 主图与当前选择先于长说明 |
| 看参数需要逐个展开或找系列详情 | 当前单品的材质、尺码摘要直接可读，完整资料图可放大 |
| 完整 SKU 是第一道门槛 | 尺码可暂不选；不借任意 SKU 代表未知规格 |
| 每次经过选图、预览与完整编辑 | 明确单品直接加入心愿；低频资料调整按需进入 |
| 完成逐件保存后才能表达喜欢 | 一次明确动作保存到现有 `ItemStatus.WISHED` |
| 回执以逐件编辑进度为中心 | 回执为“已加入心愿 · 查看”，保留逛选上下文 |

## 页面层级与最短实际动作

### 1. 广场：看得见商品的逛选入口

沿用广场底栏位置与标准顶栏。保留搜索、上新/再贩/现货/尾款以及店铺筛选；颜色、风格、单品/小物/组合放进按需筛选，不叠成持续占屏的控制面板。导入资料包留作顶栏低频动作，空目录时才成为主要操作。

商品卡以真实图片为主，下面依次为店铺、系列/商品名、售卖状态与本批日期、明确标记阶段的来源报价。日期不是联网排序证据；“预热”“现货掉落”“尾款”等按资料实际语义呈现。卡片点击进入商品详情，标题和图片共享同一目的。资料标识、SKU 数量、采集术语不成为卡片主文案。

本轮不默认在系列卡上放一个会猜选 JSK 或整个套餐的快捷收藏按钮。卡片尚不能确定用户喜欢哪件时，先让用户看到并选择具体对象。

### 2. 商品详情：图片、单品、参数构成一个连续对象

标准顶栏为“商品详情”或当前商品短名。内容顺序如下，底部固定主要操作。

1. 当前单品大图与图片页数，点击完整查看及放大。首屏必须出现能辨认主体的图片，不能先用多个资料区块把它推走。
2. 店铺与商品名称，当前售卖状态/批次日期；报价旁直接标出全款、定金、区间、组价或未知，不让用户到来源折叠中才发现阶段。
3. 可点的单品缩略选择器，例如 JSK、KC、内搭；选中状态包含图与名称。切换后主图、可用颜色、参数、报价适用范围及加入对象同步切换。
4. 当前单品颜色与可选尺码。颜色来自明确映射，不能用整搭照片颜色推断小物颜色。尺码包含“暂不选尺码”，可以先收藏后补。
5. 当前单品参数：已知材质、尺寸/尺码资料、包含内容和必要限制。摘要直接显示，完整尺码表与细节图继续向下看或点击放大；洗护、工艺、系列完整说明按需展开。
6. 售卖批次、完整系列原图与商品来源在下方。保留原始明文、公开链接、采集日期及非实时提示；内部商品 ID、版本号等只在必要来源明细出现，不挤占浏览。

“图片”不是四种文件角色的管理面板。当前单品图库默认按已核验映射组织；系列合照以“系列搭配图”身份可看，不能静默充当 KC 独立图。没有独立图时直接说明“暂无这件的独立图片”，系列参考仍可查看。未知参数标“未提供”，不补造事实。

首屏具体高度由艺术稿与原生对照共同确定。完整 Fit 与合理屏幕上限优先于无限放大图框；长图在详情显示可识别预览，并能打开完整原图。缩略图解码或展示裁切不能改动源文件。

### 3. 加入心愿：简单对象直接保存，复杂意图就地选择

当前浏览对象已经是明确单品时，固定按钮“加入心愿”直接保存。**不先弹确认、不要求选择尺码、不打开完整编辑器、不要求用户逐张检查默认图片。** 按下时显示真实保存状态，成功保持详情当前图/单品/颜色与滚动位置。

若当前仍是系列或包含多部件的购买组合，按钮打开一张轻量选择面板：

- 明确显示“这次想加入哪件”，每项用真实缩略图和名称，不列原始 SKU 长字符串；只预选用户当前已明确浏览的那件。点“选多件”进入时直接展开可勾选对象，规格按需后补，不把真正多选藏在折叠项中再先呈现当前单件编辑。系列概览没有明确对象时不擅自全选。
- 可勾选其他实际包含部件。主动作写明“加入心愿（2 件）”，默认分别成为两件物品。
- “合为一件”是按需选项，可展开名称与组身份，最终动作“合为 1 件加入心愿”。采用同系列个人心愿组合：可从本系列多个明确单品链接挑选想一起收藏/搭配的对象，不受某一个销售 SKU 包含范围限制。明确标为用户组合，不冒充商家 SKU 或购买套餐，不生成组合总价、全款阶段、主件小物或衣橱套装关系；各件独立图片、颜色、尺码与来源。
- 自主挑选已核验小物仍成立。小物独立资料和未知规格分别保留，不因与裙子一起选中继承裙码。
- “调整图片与资料”为低频入口，默认值来自精确映射。取消调整返回面板，取消面板回到商品详情，不产生半成品物品。底栏次级入口使用可读标签“选多件”，不只显示一个含义含混的加号。

选颜色与尺码是决定想要哪件的可选辅助。来源包含多种不可混淆款式或材质时，以可看图的明确款式选择解决对象歧义；不借“可以后补”掩盖用户根本不知道将保存哪件。未知尺码与未知材质本身不应阻止心愿保存。

### 4. 成功、查看与返回

成功提示“已加入心愿”，提供“查看”。单件打开现有 `ItemDetail`，多件提供本次加入清单并可逐件打开现有详情；从清单可到已有心愿页。主按钮对相同对象改为“已在心愿 · 查看”。

“查看心愿”进入已有首页心愿内容，不创建第二套收藏库。导航需要增加明确选择心愿 Tab 的入口/参数，不能仅跳首页后让用户自己寻找。查看某件优先直接开现有物品详情；返回后恢复广场原商品、图片、选择与滚动。加入成功不自动跳编辑，也不自动跳走打断逛选。

已有物品后来变为已拥有或待付款时，显示“已登记 · 查看”；再次点击不改回心愿。需要再次买同款时使用既有复制/登记能力，不把重复点心形当作再买一件。

| 场景 | 必需动作（从已进入广场起） |
| --- | --- |
| 明确单品，默认颜色，尺码暂不选 | 点商品卡 → 点加入心愿，共 2 次 |
| 系列页切换 KC 再加入 | 点商品卡 → 点 KC → 点加入心愿，共 3 次 |
| 查看另一颜色 | 在详情点颜色即换图与参数，无须先进入登记流程 |
| 看尺码/材质 | 在详情直接阅读摘要；点资料图看完整原图，不进入编辑 |
| 同时喜欢两件 | 点加入面板 → 勾选第二件 → 点加入心愿（2 件），一次提交 |
| 自主合组 | 点选多件 → 同系列勾选 → 主动选择合为一件 → 加入，名称可后补修改 |
| 去看保存结果 | 成功提示点查看；返回继续原处浏览 |

## 数据与实现可行性审查

### 可直接复用的部分

- 心愿就是现有 Item 的 `WISHED` 状态，已有列表、详情、搜索、优先级、统计与试衣选择，不新增一套收藏实体。
- `Item.size` 可空，`colors` 可空，`specificationsJson` 可保留未知；心愿不需要订单、付款日期、位置或价格。`ItemRepository.insertItem` 支持独立插入与 `importToken` 幂等。
- `Item.imageUrls`、多张尺码/资料图、完整 Fit 与全屏查看、`ImageFileHelper` 的 UUID 复制和引用保护均可复用。公开目录 AtomicFile/SHA 校验及本地原图保全继续沿用。
- `SquareProduct.suggestUnit` 的精确独立 SKU 图与 `materials` 可作为默认归属的起点；原部件范围、销售 SKU 资料与价格不下放规则继续成立。但用户组合超出单个 SKU 时需新的组模型，不能继续用旧 `SquareUnit.validate` 的单 SKU 子集校验阻止个人心愿组合。现有 token 仍需兼容。
- 已存在的 `ItemSourceRecord` 有版本化来源 JSON、显式 `imagePaths`、公开链接，已进入 ZIP/JSON 导出、预览、恢复与删除保护，可承载心愿来源，避免把内部快照全文塞进用户备注。
- 完整编辑器继续用于用户主动“编辑资料”，ItemDraft 继续服务手动编辑及已有暂停草稿。

### 必须改变的实现，不是改文案即可完成

**一、把浏览候选与实际 SKU 分开。** 当前 `SquareSku.variantId` 包含尺码，`prepare` 强制传一个实际完整 SKU。未选尺码的心愿不得借任意 S/M/L 码作为身份。新增浏览投影至少包含稳定 `browseKey`、明确部件/款式、已选颜色、候选 `skuKeys`、精确图片/资料映射和未知字段。选择完整规格后才拥有 `selectedSkuKey` 与对应报价。

投影可从明确 `part.key`、颜色、其余实际非尺码维度聚合；不能仅按名称或剥掉 SKU 尺码字符串猜同款。不同材质、不同前缀款式不混合。全款与定金链接仅通过现有已核验的系列/variant 对应合并；缺少稳定对应时应在本地目录增加可选的明确浏览映射及严格引用校验。旧 v1 没有映射仍能浏览完整系列并保存资料未定的心愿，不能重新强制走四步整理。若资料连可区分的单品都未给出，可明确保存为“本系列 · 款式待选”的一个心愿，组合/类型保留待确认，后续在同一物品补充；不擅自替用户挑第一条 SKU。

**二、加入心愿需要新的直接保存用例。** `SquareRepository.prepare` 当前只建立 ItemDraft 并返回编辑导航，不能作为完成收藏的接口。建议在 domain/usecase 中增加 `AddSquareWishUseCase`，由 SquareViewModel 调用，围绕现有 Repository/DAO 完成冻结请求、图片准备、有效外键解析与事务提交。不要让 Composable 或新的页面复制 Item 编辑器的整段保存逻辑。

Item 的品牌与类型为非空外键。当前 `prepare` 匹配失败先填 `0L`，靠用户编辑后补，因此不能直接照搬后 commit。品牌可复用 `BrandRepository.ensureUnsetBrand()`；类型应优先按稳定 `CategorySemantic` 和本地明确映射匹配，不能只比中文名称。确实不明时创建/复用语义 `UNCONFIRMED` 的“待确认”类型；当前预设初始化特意排除此项，实施不能假设已有。不能给未知组合随便套上第一件裙子的类型。该路径必须能保存，未知细节留待后补，不让必填类型变成新的收藏门槛。

**三、保留当前账本边界。** 保存为 WISHED、默认中优先级、无位置、无主件、无衣橱套装归属；明确双/组身份按实际来源保留，不创建关系。同系列个人组合保存为一个用户心愿组；组内保留成员及独立来源/图片/颜色/尺码，不将成员的某个尺码写成整个组的共同尺码。组以一个 Item（明确成组）进入现有心愿；成员数组在来源快照中版本化保存，原物品详情需能查看各成员图片/规格，不只显示一个无法拆解的组合名称。选择“分别加入”才生成独立成员 Item，合组本身不暗中再生成成员物品或关系。商品报价只进来源快照；本轮不自动创建 Price、Payment、OrderBinding 或独立参考价。因而心愿参考总价也不把来源报价自动累计进去。可在心愿详情看见“来源报价”及阶段，用户以后主动采用才进入现有价格流程。

**四、来源与图片归属结构化保存。** 公开目录全量原图继续本地保留。加入物品只把已核验的对应单品图/资料图放入该物品图库；无独立图可无图保存，不能以强制人工选图补救默认资料质量。完整系列资料作为来源可查，不冒充该件参数或图库。

来源快照包含设计/批次/来源商品、浏览对象、原始候选、已选/未选规格、价格阶段、映射版本、明文来源和图引用索引。同系列个人组增加用户组合身份与成员数组，每个成员分别记录明确单品链接、图片索引、颜色/尺码及是否仍未知；组封面取实际所选成员或用户主动指定的参考图，不使用被取消成员。新增 `ItemSourceRecord.kind = SQUARE_WISH`；图片路径显式进 `imagePaths`，JSON 用索引而非私有绝对路径。备份后的独立心愿不能只剩指向另一个公开目录的易失路径：该心愿采用的图片和必要系列证据随来源记录进入原图片体系；剩余未采用的公开目录原图仍由广场保留，目录整包不混入私人衣橱备份。多个输出共享同一来源原图副本时，必须复用现有引用保护，不能删除一件便清掉另一件证据。

### 去重、修改与旧资料

完整 SKU + 原部件范围的旧身份继续先查现有 `importToken`，不得让已保存 2.73.1 物品重新出现“尚未加入”。旧暂停草稿保留“继续整理”，不能未经确认把用户未完成的草稿当作收藏完成，也不能覆盖其手动图片/名称。

未选尺码使用明确的浏览心愿身份，区别于完整 SKU。稳定键应基于已核验商品/系列关联、部件集合与用户已选非尺码规格，不包含名称、封面、价格、目录 revision 或此次请求 UUID。用户随后在同一 Item 后补尺码是更新原记录，保留原导入身份；不是再点收藏新建。

同一对象从已知尺码回到未选尺码、多个颜色、单件与个人组合之间的重叠不能仅靠不同 token 放任新增：提交前查来源候选/部件覆盖，精确命中就显示原记录，范围重叠就给出“已有相关心愿 · 查看”；用户明确选择另一颜色或另一尺码时才允许独立心愿。用户组合的稳定键按成员身份排序，并纳入每个成员已选颜色/尺码，不以点击勾选顺序、主浏览图或某件裙码定义整个组。不同销售批次保持来源差别，只有明确同款关联才提示相关记录；不按相似名字自动合并。已删除物品后再次主动加入允许新建，不自动复活，也不保留一个永远无法清除的已收藏状态。

### 原子保存、生命周期与失败

单件与一次面板内多件的请求都在提交时冻结：目录 revision、来源/部件、颜色、尺码状态、分件/组合模式和本次输出集合。切换浏览对象不能让在途请求变成另一件。

图片复制在提交前完成并由暂存引用或持久清单保护；一笔 Room 事务内重读品牌/类型/已有 token，写入本次 Item 与对应来源记录。多件按一次用户动作全成或全不成，失败显示实际未加入，不能弹“2 件已加入”却只落一件。原四步整理的逐件非原子行为不能直接冒充新面板的一次保存。

重复点击、旋转、真实 NavHost 往返与进程终止后恢复必须按稳定业务身份查询回执。提交未完成不显示成功；提交完成但 UI 回执丢失，重新读取已有 Item 即显示“已在心愿”。文件复制失败、空间不足或事务回滚清理本次无引用副本，不动公开目录或其他物品。进程中断的复制清单启动时只清理无引用暂存，不扫除正式原图。

### Room、公开包与备份版本建议

本设计没有新业务实体或 Item 列的必然需求；复用现有 Item、ItemSourceRecord、原图片字段后，可保持 Room34/45实体，实际实施如新增表/列必须另写迁移，不因本文件预先升版本。

公开包可继续 v1，新增可选浏览映射应做字段长度、数量、真实 SKU/部件/图片引用和精确归属校验；旧包缺失字段不阻止浏览心愿。

备份不是无影响：当前 `OrderImportBackupValidation` 仅接受 `ORDER_IMPORT` 与 `PRODUCT_SUPPLEMENT` 两类来源。新增 `SQUARE_WISH` 必须补版本化快照验证、显式图片映射、未知候选/去重身份恢复、预览统计和 CSV 可读来源。建议随新来源协议升备份格式16，接受旧1—15缺失新来源；Room无需因此升级。不能把新种类伪装成 PRODUCT_SUPPLEMENT 规避校验，也不能在报告声称仍为备份15且完全兼容旧应用。旧版本应用不承诺读取新备份。
