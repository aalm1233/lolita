# 每个旧版本直升当前库的核查

用户现场：小米 MIX Flip 2，广场服务地址入口仍退出，JSON 导出中途也直接退出。用户要求同时考虑多次升级，并逐一分析每个版本直升。此前 2.71.1→2.78.0 是 Room34→34，不能代表旧数据库迁移。

## 已执行与结论边界

当前迁移实现从每个数据库版本 **1–33→34** 独立回放，并增加 **34→34** 对照；34 个起点均实际读取 Room DAO、导出 JSON、重新预览 JSON、打开广场地址输入并取消。所有起点通过，终点图片 SHA 保持。**v1 没有留存 schema 导出**，它是依据 `f5a2cf1c→9a36ae8c` 的实体差异，从 v2 仅移除当时新增的四列重建，单列为源码推导夹具；v2–34 使用仓库原有 Room schema。

每个夹具含 5 件旧物品、5 条价格、1 条已付但日期未知的付款、品牌、类型、套装、穿搭关系和真实 PNG；保留含引号/反斜杠/换行的颜色、原说明、负数历史归档金额、未知付款日期。JSON 导出调用实际 `BackupManager` 和 ContentResolver，广场使用实际 `SquareRepository→SquareViewModel→SquareScreen`。独立数据库与图片目录，不操作用户设备或私人库。

另执行两种已发布迁移代码链：20→21→…→34 每次关闭重开，以及20→23→26→30→34；20→21、21→22、22→23和后续各段来自当时版本源码，测试夹具记录 tag、完整提交和源文件 SHA，不用后来修改的迁移替代旧代码。中间版本28/29写入旧v1/v2任务请求，30写入旧物品草稿，再继续升级与导出。当前代码6→10→13→15→18→20→23→26→29→30→31→32→33→34也通过。

**这不是每个历史 APK 的安装实测**。原生回放运行在独立 Android15/API35 AVD；不会执行中间旧 App 的所有业务刷新、恢复备份、系统文件授权或厂商定制。不能据此宣布小米两处退出已修复，也不能排除用户实际历史内容、进程内存或 OEM 问题。

## 已升级用户的特殊风险

迁移只在跨库版本时运行。曾经执行旧SQL留下的问题，不能靠修改同一个 `MIGRATION_x_y` 自动回补。测试专门构造了库20中已经残留的损坏颜色JSON，再逐版升34：原值保留，JSON导出返回被捕获的失败，广场服务弹窗仍能打开；没有复现进程退出。因此该风险成立，但还不能当作用户现场根因，更不能删除数据或放宽备份校验来掩盖。

当前11→12/12→13的颜色修复、14→15的单图编码、17→18的NULL处理和20→21的搬表保全尤其需要区分“当前实现”与“用户曾经执行的实现”。早期原代码执行过的子记录丢失也无法从现有库凭空恢复。20→34已发布代码回放通过不等于所有早期已发布业务状态均可重建。

仓库87个标签全部已读取，GitHub85条正式发布记录均有本地标签；`v2.20`、`v2.36.11`只有本地标签，没有本次查询中的公开Release。`v2.13.0`标签源码自报版本是`2.12.3/26`，必须保留这个差异，不把标签源码等同于附件身份。完整逐标签表见下方，原始提交映射和39个原生子场景回执见 [JSON回执](square-all-upgrade-paths-2026-11-07.json)。

仍需要手机真实异常栈/系统退出原因。2.78.2仅加入本机脱敏诊断导出，便于复现一次后定位；不宣称修复两处闪退。记录范围、隐私和界面图见[诊断计划](plans/2026-11-07-crash-diagnostics.md)。
